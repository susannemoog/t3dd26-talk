Entwicklerarbeit in mehreren Projekten — orchestriert mit herdr

Susi MoogTYPO3camp Berlin · 30 Minuten
Guten Morgen! Ich bin Susi, Entwicklerin bei neusta. Ich arbeite gleichzeitig in neun Repositories — eine Demo-Landschaft mit TYPO3, Strapi, Payload, Pimcore, Storyblok, Contentful, Magnolia. Neben der eigentlichen Arbeit stapeln sich dort Aufgaben, die in kein Sprint-Ticket passen: Scaffolds, MR-Reviews, Update-Tests, Seeder, CI. Diese Session ist die Geschichte, wie ich diesen Teil des Jobs parallelisiert habe.

Ausgangslage

Neun Projekte, ein Backlog

  • MR-Reviews — 3 offen
  • Composer-Updates — testen, mergen
  • Projekt-Scaffolds — mit CI
  • Content-Strukturen & Seeder — TCA, Templates
  • wöchentliche Update-Runde — 9 Repos
Die Ausgangslage: neun Projekte, und neben der eigentlichen Arbeit ein Backlog. Drei offene MR-Reviews. Composer-Updates, die getestet werden wollen. Projekt-Scaffolds mit CI. Content-Strukturen und Seeder für die Demos. Und wöchentlich die Update-Runde über alle neun Repos. Das ist der Teil des Jobs, der nie fertig wird — weil er sequentiell ist und die Zeit fehlt.

Das Werkzeug

herdr — ein Terminal-Workspace-Manager

  • Workspaces → Tabs → Panes
  • erkennt Coding-Agenten — 20+ Typen: pi, claude, codex, gemini …
  • Lebenszyklus als API — nicht Screen-Scraping
Das Werkzeug heißt herdr: ein Terminal-Workspace-Manager. Terminals in einer Struktur — Workspaces, Tabs, Panes. Und der entscheidende Teil: herdr erkennt Coding-Agenten. Über zwanzig Typen — pi, claude, codex, gemini, cursor. Pro Pane ein anderer möglich. "Erkennt" heißt: Der Agent ist kein anonymer Prozess in einem Terminal, sondern ein Objekt mit Namen, Zustand und Schnittstelle. Ohne diese Erkennung wäre Orchestrierung Screen-Scraping.

Agent-Zustand

Vier Zustände, als API-Ergebnis

working idle blocked done
  • blocked → Agent fragt — ich entscheide
  • done → Ergebnis liegt in der Datei
Jeder Agent bekommt einen Lebenszyklus, der als API-Ergebnis lesbar ist: working, idle, blocked, done. blocked ist der wichtige Zustand: Der Agent steht an einer Frage oder Freigabe — dann entscheide ich. done heißt: Der Auftrag ist abgeschlossen, das Ergebnis liegt in der Datei.

Steuerung

Eine kleine API pro Agent

  • herdr agent start seeder --kind pi --pane <id>
  • herdr agent prompt seeder "<auftrag>" --wait
  • herdr agent wait seeder fixer --until done
  • herdr agent read seeder
Über die Agenten legt herdr eine kleine API: agent start — Agent starten, Typ und Pane gewählt. agent prompt — Auftrag geben, mit --wait auf den Abschluss. agent wait — auf einen Zustand warten. agent read — die Ausgabe lesen. Weil es eine API ist, kann ein Agent sie selbst bedienen: Meine Steuer-Session promptet andere Agenten. Das ist die Basis der ganzen Orchestrierung.

Abgrenzung

herdr-Agenten vs. Subagenten

Subagent
  • innerhalb meiner Session
  • Ergebnis füllt meinen Kontext
  • erbt Modell & Regeln
  • gebunden an meine Laufzeit
herdr-Agent
  • eigene Session, eigenes cwd
  • eigene Projekt-AGENTS.md
  • beliebiger Agent-Typ je Pane
  • Zustand & Ausgabe als API
Die Abgrenzung zu Subagenten — die Agent-Funktion im eigenen Tool. Ein Subagent läuft innerhalb meiner Session, sein Ergebnis fließt in meinen Kontext zurück, er erbt Modell und Regeln, und er stirbt mit meiner Session. Ein herdr-Agent ist eine eigene Session: eigenes Arbeitsverzeichnis, eigene Projekt-AGENTS.md, beliebiger Agent-Typ je Pane. Sein Zustand und seine Ausgabe sind API-Ergebnisse. Kurz: Subagenten sind Delegation innerhalb eines Agenten — herdr ist Orchestrierung über mehrere.

Feature

Git-Worktrees pro Agent

t3-Demo
eine Codebasis, ein Remote
wt-t3-seeder
Content-Element + Seeder
TCA-Schema via dev-companion
wt-t3-viewhelper
ViewHelper-Fix
12 Unit-Tests, rot zuerst

herdr worktree create --branch wt-t3-seeder

Das Feature für Entwickler: herdr verwaltet Git-Worktrees. herdr worktree create legt einen Worktree an — eigenes Verzeichnis, eigener Branch, dieselbe Codebasis. In der Demo: Agent A baut im Worktree wt-t3-seeder das Content-Element mit Seeder — das TCA-Schema fragt er über den typo3-dev-companion ab. Agent B fixt im Worktree wt-t3-viewhelper einen ViewHelper, mit Unit-Tests, rot zuerst. Parallel an derselben Codebasis, ohne Konflikt — klassisches Git.

Weitere Features

Maschinen & Benachrichtigungen

  • Maschinen-Forwarding — dieselben Befehle über SSH auf entfernter Maschine
  • Notifications — herdr notification show, wenn ein Agent fertig ist oder fragt
  • Panes als Terminals — Befehle, Server, Tests neben Agenten
Zwei Features, die aus dem lokalen Werkzeug etwas Größeres machen: Maschinen-Forwarding: herdr steuert über SSH verbundene Maschinen — gleiche Befehle, entfernter Rechner. Der Agent arbeitet auf der Maschine, auf der das Projekt läuft. Notifications: herdr notification show benachrichtigt, wenn ein Agent fertig ist oder auf eine Freigabe wartet. Das ist der Moment, in dem ich nicht auf neun Terminals starre, sondern gerufen werde, wenn es etwas zu entscheiden gibt.

Der Workflow

Ein Agent pro Aufgabe

  • ein Agent pro Aufgabe — Review, Update, Scaffold, Seeder
  • Batches von 5 — API-Limit, nicht herdr
  • Ergebnis in eine Datei — Antwort nur „DONE“
  • Audit bei mir — Berichte lesen, mergen oder liegen lassen
Der Workflow darauf: Ein Agent pro Aufgabe — nicht ein Agent mit einer Liste. Review, Update, Scaffold, Seeder: je eine Sache zu Ende gebracht. Beauftragt in Batches von maximal fünf, wegen des API-Limits. Jeder Agent schreibt sein Ergebnis in eine Datei und antwortet nur mit DONE — Pane-Output ist keine verlässliche Schnittstelle. Und das Audit bleibt bei mir: Berichte lesen, MRs prüfen, mergen oder liegen lassen.

Stolpersteine

Was schiefgeht

  • Concurrency-Limit 5 — Agent Nr. 6 bekommt ein 429
  • Pane-Output — keine Schnittstelle; Dateien, immer Dateien
  • unvorsichtige Agenten — machen echte Git-Historie; Regeln in der AGENTS.md
  • paralleles Fehlverhalten — falscher Kontext × 9 = 9 falsche Ergebnisse
Was schiefgeht: Das Concurrency-Limit — Agent Nummer sechs bekommt ein 429 und existiert nicht, das dauerte, bis ich es verstanden hatte. Pane-Output ist keine Schnittstelle — nicht eingesammelte Antworten sind weg, deshalb Dateien. Ein unvorsichtiger Agent macht echte Git-Historie — deshalb stehen Deployment- und Commit-Regeln in der AGENTS.md jedes Projekts, nicht im Prompt. Und Parallelität bedeutet auch paralleles Fehlverhalten: Mehrere Agenten mit demselben falschen Kontext sind mehrere falsche Ergebnisse. Der Kontext muss vor dem Start stimmen.

Fazit

Drei Sätze

  • Orchestrierung braucht Schnittstellen — Zustand, Prompt, Ausgabe
  • Worktrees für Parallel-Arbeit — ein Agent pro Branch, eine Codebasis
  • Die Verträge schreibt man selbst — AGENTS.md, Limits, Audit
Drei Sätze zum Mitnehmen: Orchestrierung braucht keine Intelligenz, sondern Schnittstellen — herdr macht Agenten steuerbar über Zustand, Prompt und Ausgabe. Worktrees sind der Schlüssel für echtes Parallel-Arbeiten: ein Agent pro Branch, eine Codebasis, null Konflikt. Und die Verträge schreibt man selbst — AGENTS.md pro Projekt, Concurrency-Limits, Audit bei mir. Das Werkzeug liefert die Mechanik, die Disziplin liefert man.
