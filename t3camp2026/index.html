Das Werkzeug

herdr — ein Terminal-Workspace-Manager

  • Workspaces → Tabs → Panes
  • erkennt Coding-Agenten — 20+ Typen: claude, codex, gemini, pi …
  • Lebenszyklus als API — nicht Screen-Scraping

herdr.dev

Mein Werkzeug dafür ist herdr, von herdr.dev: ein Terminal-Workspace-Manager. Terminals in einer Struktur — Workspaces, Tabs, Panes. Der entscheidende Teil: herdr erkennt Coding-Agenten. Über zwanzig Typen — Claude Code, Codex, Gemini, Cursor und pi, ein schlanker Coding-Agent fürs Terminal. Pro Pane ein anderer; bei mir laufen pi, claude und codex im Wechsel. „Erkennt“ heißt: Der Agent ist kein anonymer Prozess, sondern ein Objekt mit Namen, Zustand und Schnittstelle. Vorher habe ich Agenten-Ausgaben per Hand aus dem Terminal gelesen — genau das Screen-Scraping, das ich loswerden wollte. Merkt euch zwei Wörter für heute: orchestrieren und wirksam machen. Das erste ist herdr. Das zweite kommt beim TYPO3-Teil.

Agent-Zustand

Vier Zustände, als API-Ergebnis

working idle blocked done
  • idle → wartet auf den nächsten Auftrag
  • blocked → Agent fragt — ich entscheide
  • done → Ergebnis liegt in der Datei
Jeder Agent hat einen Lebenszyklus, den ich als API-Ergebnis lese: working, idle, blocked, done. idle heißt: Er wartet auf den nächsten Auftrag. blocked ist der Zustand, auf den ich warte: Der Agent steht an einer Frage oder Freigabe — dann entscheide ich. In meiner letzten Update-Runde waren vier Agenten gleichzeitig blocked; alle vier hatte ich in fünf Minuten abgehandelt. done heißt: Auftrag abgeschlossen, das Ergebnis liegt in der Datei.

Steuerung

Eine kleine API pro Agent

  • herdr agent start a11y --kind pi --pane <id>
  • herdr agent prompt a11y "<auftrag>"
  • herdr agent wait a11y --until done
  • herdr agent read a11y
Über die Agenten legt herdr eine kleine API: agent start — Agent starten, Typ und Pane wählen. agent prompt — Auftrag geben; mit --wait wartet der Aufruf gleich mit. agent wait — warten, bis ein Zustand erreicht ist. agent read — die Ausgabe lesen. Weil es eine API ist, kann ein Agent sie selbst bedienen: Meine Steuer-Session — im Video heißt sie controller — startet und promptet die anderen Agenten, in Batches. Ich formuliere den Auftrag einmal pro Runde.

Abgrenzung

herdr-Agenten vs. Subagenten

Subagent
  • innerhalb meiner Session
  • Ergebnis füllt meinen Kontext
  • erbt Modell & Regeln
  • gebunden an meine Laufzeit
herdr-Agent
  • eigene Session, eigenes cwd
  • eigene Projekt-AGENTS.md
  • beliebiger Agent-Typ je Pane
  • Zustand & Ausgabe als API
Die Frage kommt immer: Warum nicht einfach Subagenten — die Agent-Funktion im eigenen Tool? Ein Subagent läuft innerhalb meiner Session, sein Ergebnis fließt in meinen Kontext zurück, er erbt Modell und Regeln, und er endet mit meiner Session. Bei neun Repos heißt das: neun Berichte in einem Kontext. Ein herdr-Agent ist eine eigene Session: eigenes Arbeitsverzeichnis, eigene Projekt-AGENTS.md, beliebiger Agent-Typ je Pane. Zustand und Ausgabe sind API-Ergebnisse. Kurz: Subagenten sind Delegation innerhalb eines Agenten — herdr ist Orchestrierung über mehrere.

Feature

Git-Worktrees pro Agent

eine Codebasis, ein Remote

Kontraste gegen WCAG 2.1 AA
wt-talk-script

Das Feature, das mir am meisten gebracht hat: herdr verwaltet Git-Worktrees. herdr worktree create legt einen an — eigenes Verzeichnis, eigener Branch, dieselbe Codebasis. Im ersten Video seht ihr das an meinem ehrlichsten Testfall: dem Repo dieses Talks. Agent a11y prüft im Worktree wt-talk-a11y die Farbkontraste der Slides gegen WCAG 2.1 AA. Agent scripter überarbeitet im Worktree wt-talk-script dieses Sprechskript. Beide parallel an derselben Codebasis, ohne sich in die Quere zu kommen — klassisches Git, das ich vorher nie so genutzt habe.

Der Sonderfall

Warum TYPO3 anders ist

  • Die Daten liegen hinter TCA-Definitionen — nicht hinter einem JSON-Endpunkt
  • Der DataHandler validiert, was reingeht — Tabelle, PID, Sprache, Versionierung
  • Die Konventionen stehen im Core — Translation-Domains, TCA-Formen, Changelog-Regeln

Ein reiner API-Agent weiß davon nichts — er bräuchte Schemata, Datensätze, Regeln.

Warum ist TYPO3 der Sonderfall? Die Daten liegen nicht hinter einem JSON-Endpunkt, sondern hinter TCA-Definitionen. Der DataHandler validiert, was reingeht — Tabelle, PID, Sprache, Versionierung. Und die Konventionen stehen im Core: Translation-Domains, TCA-Formen, Changelog-Regeln. Ein reiner API-Agent weiß davon nichts. Er bräuchte Schemata, Datensätze, Regeln — genau die liefert der typo3-dev-companion.

Der Workflow

Ein Agent pro Aufgabe

  • ein Agent pro Aufgabe — Review, Update, Scaffold, Seeder
  • Batches von 5 — dann die nächsten
  • Ergebnis in eine Datei — Antworten sind keine Schnittstelle
  • Audit bei mir — Berichte lesen, mergen oder liegen lassen
Mein Workflow darauf: ein Agent pro Aufgabe — nicht ein Agent mit einer Liste. Review, Update, Scaffold, Seeder: je eine Sache, zu Ende gebracht. Beauftragt in Batches von höchstens fünf. Jeder Agent schreibt sein Ergebnis in eine Datei — ihr habt eben gesehen, warum. Und das Audit behalte ich: Ich lese die Berichte, prüfe die MRs und entscheide über jeden Merge.

Qualität

Der Review-Loop: coder baut, brain prüft

  • coder entwickelt — Modell-Profil fürs Schreiben
  • brain reviewt in frischer Session — anderes Profil, ohne Entstehungskontext
  • Befunde zurück an coder — berechtigt → Fix, unberechtigt → Begründung
  • Orchestriert mit herdr — ich kann in jede einzelne Session eingreifen

herdr agent prompt brain "Reviewe den letzten Commit …"

Der Kern meines Workflows: coder und brain sind bei mir zwei Modell-Profile — coder schreibt, brain prüft. Mit coder entwickle ich. Dann reviewt brain denselben Stand in einer frischen Session — ohne den Entstehungskontext. Ein Modell ist gegenüber seiner eigenen Lösung systematisch unkritisch; wer den Entstehungsweg nicht kennt, liest den Code mit fremdem Blick. Die Befunde gehen zurück an coder: berechtigt wird gefixt, unberechtigt wird begründet. Beide laufen in eigenen herdr-Panes — ich kann in jede Session eingreifen.

Stolpersteine

Was schiefgeht

  • Concurrency-Limit 5 — Agent Nr. 6 bekommt ein 429
  • Pane-Output — keine Schnittstelle; Dateien, immer Dateien
  • unvorsichtige Agenten — machen echte Git-Historie; Regeln in der AGENTS.md
  • paralleles Fehlverhalten — falscher Kontext × 9 = 9 falsche Ergebnisse
Was ich selbst habe schiefgehen lassen: Beim ersten Lauf habe ich sechs Agenten gestartet. Der sechste bekam ein 429 und existierte einfach nicht — zwanzig Minuten habe ich gesucht, bis ich das Limit verstanden hatte. Und ich habe drei Agenten-Berichte verloren, weil ich sie nur im Pane-Output hatte — seitdem schreibt jeder Agent in eine Datei. Ein Agent hat mir in die falsche Git-Historie committet — seitdem stehen Commit- und Deployment-Regeln in der AGENTS.md jedes Projekts, nicht im Prompt. Und ich habe zweimal denselben falschen Kontext an mehrere Agenten verteilt: Parallele Arbeit heißt auch paralleles Fehlverhalten. Der Kontext muss vor dem Start stimmen.

Qualität

Meine Quality Gates

  • Test-first, wörtlich — Test reproduziert den Bug, rot gesehen, dann Produktionscode
  • Unit-Tests immer — Vitest/Jest für TypeScript, PHPUnit für PHP
  • Playwright pro Umgebung — lokal in ddev und auf jedem Zielserver
  • Coverage misst nicht Prüfung — 98 % sagen nichts über die Assertions
  • Stop-Punkte beim Menschen — Push, Merge, Audit: meine Entscheidung
Weil parallele Agenten auch parallel fertig werden, brauche ich Quality Gates. Erstens Test-first, und zwar wörtlich: Jeder Bugfix beginnt mit dem Test, der den Bug reproduziert. Ich sehe ihn rot, erst dann fasse ich Produktionscode an. Der Test ist der Vertrag, der das Modell an die Realität bindet. Unit-Tests immer: Vitest und Jest für TypeScript, PHPUnit für PHP. Verändertes Verhalten ohne Test geht nicht raus, auch nicht aus einem Agenten. Fürs Frontend Playwright, mit einem Project pro Umgebung: lokal in ddev und auf jedem Zielserver. Smoke-Tests prüfen das Deployment, Task-Tests das Ergebnis redaktioneller Änderungen. Coverage ist dabei kein Maß: 98 Prozent sagen nichts über die Assertions. Und die Stop-Punkte bleiben bei mir: Push und Merge entscheide ich — eine frühere Freigabe gilt nicht für neue Commits. Mehr Prozess braucht eine Person mit neun Agenten nicht.

Verträge

Was in meiner AGENTS.md steht

  • Commit-Identität pro Remote — per Repo-Config, nie per --author
  • glab statt curl — MRs, Pipelines, API über ein Werkzeug
  • Worklog pro Aufgabe — eine Zeile in ~/worklog, vom Agenten gepflegt
  • herdr-Regeln — ein Agent pro Projekt, Pane-IDs aus der JSON-Antwort, Batches von 5
Was ihr direkt mitnehmen könnt: was bei mir in der AGENTS.md jedes Projekts steht. Erstens die Commit-Identität pro Remote — GitHub und GitLab bekommen meine private Adresse, alles Neusta-interne die Firmenadresse. Per Repo-Config gesetzt, nie per --author überschrieben. Ohne diese Regel committet ein Agent mit der falschen Identität — das hatte ich. Zweitens: glab statt curl. Ein Werkzeug für MRs, Pipelines und API — dann erfindet der Agent keine Endpunkte. Drittens mein Worklog: eine Zeile pro Aufgabe in ~/worklog, vom Agenten selbst gepflegt — die Basis meiner Zeiterfassung. Und viertens die herdr-Regeln: ein Agent pro Projekt, Pane-IDs aus der JSON-Antwort statt geraten, Batches von fünf.

Fazit

Drei Sätze

  • Orchestrierung über Schnittstellen, nicht über Intelligenz — Zustand, Prompt, Ausgabe
  • Worktrees für Parallel-Arbeit — ein Agent pro Branch, eine Codebasis
  • Die Verträge schreibt man selbst — AGENTS.md, Limits, Audit
Drei Sätze zum Mitnehmen. Erstens: Ich orchestriere über Schnittstellen, nicht über Intelligenz — herdr gibt mir Zustand, Prompt und Ausgabe meiner Agenten als API. Zweitens: Worktrees bringen echtes Parallel-Arbeiten — ein Agent pro Branch, eine Codebasis. Drittens: Die Verträge halte ich selbst fest — AGENTS.md in jedem Projekt, fünf Prompts pro Batch, das Audit bei mir. Das Werkzeug liefert die Mechanik, die Disziplin bringe ich.

Ausblick

Gleiches Muster für Ticketsysteme

  • der gesamte Workflow — vom Ticket bis zum MR
  • Zugriff über API oder custom MCP — wie bei den CMS: API, wo sauber; MCP, wo nötig
  • Tickets lesen — Kontext für den Agenten vor dem Start
  • kommentieren & pflegen — der Agent schreibt zurück ins Ticket
Dasselbe gilt letztlich für jedes Ticketsystem — und zwar für den gesamten Workflow, vom Ticket bis zum MR. Der Zugriff läuft wie bei den CMS: über die API, wo es eine saubere gibt, über einen eigenen MCP-Server, wo nicht. Der Agent liest das Ticket als Kontext, bevor er startet. Und er schreibt zurück: Er kommentiert und pflegt das Ticket. herdr orchestriert, das MCP macht wirksam — egal, ob das Ziel ein CMS, mein Kalender oder ein Ticket ist.
